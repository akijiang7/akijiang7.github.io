Key points

slime

English

slime is an LLM training framework designed for RL scaling. It provides two core capabilities:

  1. High-performance training: by connecting Megatron and SGLang, it supports efficient training in a variety of modes;
  2. Flexible data generation: through custom data-generation interfaces and a server-based engine, it supports arbitrary training-data generation workflows.

slime's design goal is to make these two capabilities reinforce each other while avoiding turning the system into a fragmented set of trainers, rollout services and agent frameworks. Megatron training, SGLang rollout, custom data generation, reward computation, verifier feedback and environment interaction all flow through the same training / rollout / Data Buffer path.

This makes slime one of the most battle-tested open-source RL post-training frameworks: it is lightweight, clear and easy to extend, and it has also been validated through the complete training loop behind SOTA-level model releases.

Design features

  • Production practice: slime is the RL training framework behind GLM-5.3-Flash, GLM-5.3, GLM-5.2, GLM-5.1, GLM-5, GLM-4.7, GLM-4.6 and GLM-4.5.
  • Native engine integration: Megatron arguments are used directly; SGLang arguments are passed with the --sglang- prefix.
  • Flexible data generation: plug in generation functions, reward functions, verifiers and interactive environments through custom interfaces.
  • Correctness and reliability: supports independent rollout and training debugging, reproducibility configuration, fault recovery, and CPU/GPU tests, serving long-running experiments.

Supported models

In addition to the GLM series, slime also supports Qwen (Qwen3.8, Qwen3.6, Qwen3.5, Qwen3-Next, Qwen3 MoE, Qwen3, Qwen2.5), DeepSeek (V3, V3.1, R1) and Llama 3. See scripts/models for model configurations and the online documentation for training examples.

Engine configuration and deployment

You can use Megatron's parallelism, optimizer, checkpoint and model arguments directly. SGLang arguments for the currently installed version can be passed by adding the --sglang- prefix; for example, write --mem-fraction-static as --sglang-mem-fraction-static.

For complex deployments, see:

  • SGLang configuration: configure server groups, multi-model serving and per-group parameters via YAML.
  • PD disaggregation: configure prefill and decode resources separately.
  • Incremental weight sync: transfer changed weight bytes through shared storage.
  • External rollout engines: connect inference processes managed outside the training job, with support for updating weights across different GPU clusters via disk.

Correctness, stability and CI

CPU tests cover core behavior and custom-interface contracts; GPU tests cover dense/MoE training, rollout deployment, checkpoints, precision, fully asynchronous rollout, distillation and debug replay. See the CI guide for the test matrix and how to run it.

Related engineering docs: Debugging, Reproducibility, Fault recovery, Call tracing and Profiling.

Architecture overview

(Architecture diagram: imgs/arch.png)

Modules:

  • training (Megatron): runs the main training flow, reads data from the Data Buffer, and after training synchronizes parameters to the rollout module;
  • rollout (SGLang + router): generates new data (including reward/verifier) and stores it in the Data Buffer; through custom generate, multi-turn loops, tool calls, environment/sandbox interaction and verifier-based rewards can be layered on top;
  • data buffer: the bridge module, managing prompt initialization, custom data and rollout generation methods (including agentic workflows that produce samples through the same interface).

By default, data is transferred through the Ray object-store. With --rollout-data-transport straw, straw persists prompt tasks, rollout continuation state and training batches on JuiceFS shared storage. Ray passes control messages and references, while generation and training processes read and write data directly in parallel. See the straw usage and recovery guide.

Agentic RL examples

The following agent-training examples connect to the standard rollout and data buffer through custom interfaces:

  • examples/multi_agent: multi-agent generation within the standard rollout loop via --custom-generate-function-path.
  • examples/search-r1: search/RAG-style multi-turn generation via --custom-generate-function-path.
  • examples/fully_async: fully asynchronous rollout, suited to long-tail tasks where sample-generation time varies widely.
  • examples/coding_agent_rl: coding-agent RL using Qwen3.8-27B, Xiaomi MiMo SWE data and the sunabako sandbox, keeping the official test rewards and token-level training trajectories.

For how to choose the right interface for an agent workflow, see the customization guide.

Ecosystem built on slime

These projects are not just demos. They are independent systems that use slime as a reusable RL substrate, covering production-grade post-training, agentic RL, domain RL and rollout-system research.

🐎 Dressage: scalable RL for any agent and sandbox

Dressage is an agentic RL training framework built on slime by Alibaba Accio, providing unified RL for blackbox agents (e.g. OpenCode, OpenClaw) and arbitrary sandbox environments (e.g. bwrap, E2B, Kubernetes). Through Paddock, Sandbox and Proxy layers it decouples interaction semantics, execution location and token-level trajectory capture, adapting to agent workflows without rewriting the agent's internal loop. Dressage records token-wise logprobs, loss masks, weight versions and MoE routing, and uses TITO and segment-aware training to turn long-horizon tool interactions into stable RL samples.

⛵ Miles: an enterprise-grade RL framework for large-scale model training

Miles is a large-model RL post-training framework built on slime by RadixArk. It stays closely in sync with upstream slime development while adding a series of extensions for enterprise scenarios: deeper SGLang integration, supporting operations and deployment tools and services, and optimizations for new models and new hardware. Miles also keeps iterating around real production needs, for example adding support for LoRA, TITO and low-precision training.

🔷 vime: a vLLM-native RL post-training framework based on slime

vime is a post-training framework based on slime, maintained by the vLLM project. It keeps slime's Megatron training stack, Data Buffer data flow and custom data-generation design; its main feature is replacing the rollout backend with vLLM (together with vllm-router). Starting from existing slime launch scripts, you only need to adjust rollout-related arguments to switch to vime for training.

🌈 Relax: Asynchronous RL Engine for Omni-Modal Agentic Training

Relax (Reinforcement Engine Leveraging Agentic X-modality) is an omni-modal agentic RL framework open-sourced by the RedAI Infra team, built on the slime infrastructure stack combining Ray, Megatron-LM and SGLang. Relax uses a service-oriented architecture on Ray Serve, with Megatron-LM and SGLang as the training/inference backends. It uses TransferQueue to fully decouple Actor, Rollout, ActorFwd, Reference and Advantage computation onto independent GPU clusters, and introduces DCS (Distributed Checkpoint Service), which asynchronously streams updated Actor weights to Rollout/ActorFwd/Reference through an NCCL-broadcast weight-sync engine, overlapping with the next training step, enabling fully-async training under configurable staleness. Relax supports end-to-end RL for text, vision, audio (including Qwen3-Omni) and agentic multi-turn rollout.

🦞 OpenClaw-RL: Train a Personalized Clawbot Simply by Talking to It

OpenClaw-RL is an RL server for personalized OpenClaw agents. It hosts the OpenClaw model and continuously improves it from historical conversations across deployments, while slime's decoupled RL infrastructure keeps training from interfering with API serving. It supports two automatic optimization methods: GRPO, which infers binary feedback from subsequent states, and on-policy distillation, which extracts hindsight hints from subsequent feedback.

⚛️ P1: Mastering Physics Olympiads with Reinforcement Learning

P1 is a series of open-source physics reasoning models trained entirely through reinforcement learning. P1 uses slime as its RL post-training framework and proposes a multi-stage RL training algorithm that progressively strengthens reasoning through adaptive learnability adjustment and a stabilization mechanism. Under this training paradigm, P1 achieved breakthrough performance in open-source physics reasoning.

📈 RLVE: Scaling LM RL with Adaptive Verifiable Environments

RLVE proposes using verifiable environments to scale language-model RL: environments generate problems programmatically and provide algorithmically verifiable rewards. By training jointly on 400 verifiable environments, RLVE lets each environment dynamically adapt its problem-difficulty distribution as training progresses, matching the current capability of the policy model.

⚡ TritonForge: Agentic RL Training Framework for Kernel Generation

TritonForge uses slime's SFT and RL capabilities to train LLMs that automatically generate optimized GPU kernels. Through two-stage training (supervised fine-tuning plus reinforcement learning with multi-turn compilation feedback), TritonForge achieved notable results in converting PyTorch operations into high-performance Triton kernels.

🚀 APRIL: Accelerating RL Training with Active Partial Rollouts

APRIL proposes a system-level optimization that integrates seamlessly into slime to accelerate the rollout-generation phase of RL training. By intelligently over-provisioning requests and actively managing partial completions, it mitigates the long-tail bottleneck common in rollout generation, a phase that typically consumes more than 90% of RL training time.

🏟️ qqr: Scaling Open-Ended Agents with ArenaRL & MCP

qqr (a.k.a. hilichurl) is a lightweight slime extension for evolving open-ended agents. It implements the ArenaRL algorithm, which mitigates discriminative collapse through tournament-based relative ranking (e.g. Seeded Single-Elimination, Round-Robin), and integrates seamlessly with the Model Context Protocol (MCP). qqr uses slime's high-throughput training to enable scalable, distributed agent evolution in a standardized, decoupled tool environment.

☁️ ART: Scalable and Sandboxed Agentic RL on AWS Bedrock AgentCore Runtime

ART (AgentCore RL Toolkit) is a toolkit that adapts agents from real production environments for RL training on AWS Bedrock AgentCore Runtime. AgentCore Runtime provides an agent runtime environment with auto-scaling and sandboxed isolation, which is well suited to safely running large numbers of agent rollouts in parallel. With ART, users only need to add a decorator (@app.rollout_entrypoint) to their agent code to adapt it for RL training while directly reusing the production agent harness; token capture for RL training is done at the model gateway layer. ART lists slime as one of its RL training backends, helping users easily optimize production agent models with slime's RL training algorithms.

Together, these projects reflect slime's core idea: a single high-performance RL kernel can support frontier-model post-training, online agent optimization, verifiable environments, omni-modal rollout, kernel-generation agents and rollout-system research, without changing the core training loop.

Arguments

Arguments fall into three categories:

  1. Megatron arguments: slime reads Megatron arguments directly; you can configure Megatron by passing, for example, --tensor-model-parallel-size 2;
  2. SGLang arguments: all arguments of the SGLang version installed in the current environment are supported; they must start with --sglang-, for example --mem-fraction-static must be passed as --sglang-mem-fraction-static.
  3. slime's own arguments: see slime/utils/arguments.py

For full usage instructions, see the usage documentation.

Code reading roadmap

We suggest starting from the main training loop and then tracing down layer by layer as needed:

train.py: train
├─ slime/ray/placement_group.py       Ray resource and worker initialization
├─ slime/ray/rollout.py              RolloutManager.generate: rollout orchestration
│  └─ slime/rollout/sglang_rollout.py  Sample generation and reward computation
└─ slime/ray/actor_group.py          RayTrainGroup.async_train: training scheduling
   └─ slime/backends/megatron_utils/actor.py
      ├─ model.py                    Megatron model execution
      └─ loss.py                     RL loss and advantage computation

On a first read, you can treat slime/utils/arguments.py as the configuration entry point. The deployment details in slime/backends/sglang_utils/ and the weight-sync implementation in slime/backends/megatron_utils/update_weight/ can wait until you need to modify the corresponding features.

What this means for US developers

slime is worth knowing about if you do RL post-training at scale. According to the README, it is the RL stack that Z.ai used to train its GLM models, and it supports the open-weight families US teams already fine-tune: Qwen, DeepSeek and Llama 3. Its main design choice is to send training, rollout, rewards and agent environments through one Data Buffer path instead of separate services. That makes it a sensible base for agentic RL, such as coding agents with sandboxed test rewards. The Apache 2.0 license allows commercial use. The ecosystem section shows US organizations building on it too: vLLM maintains a vLLM-native fork (vime), and AWS's AgentCore RL Toolkit lists slime as a backend. Much of the deeper documentation linked here is in Chinese, under docs/zh. An English README is also available.
