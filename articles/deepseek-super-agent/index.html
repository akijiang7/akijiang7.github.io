DeepSeek open-sources a 'Super-agent' prototype: a Router/Worker coding agent that lives in GitHub and team chat

Read the full text ↓

Key points

  • On the evening of October 31, 2026, DeepSeek's Harness team published a Chinese-language design essay, "Super-agent 设计探索：迈向更自主的 Agent 系统" ("Exploring Super-agent Design: Towards a More Autonomous Agent System"). Alongside it, they open-sourced dsh-superagent-prototype under the MIT license.
  • The prototype is a proactive coding agent for one GitHub repository, with Feishu chat as an option. It is packaged as a bundle for DeepSeek Harness.
  • A resident router session decides what to take on. Each accepted work item gets its own worker session and directory, so tasks run in parallel without interfering.
  • Authorization is enforced by the host: allowed lists, team-written rules and per-task "Mandates". Proactive work starts in an observe mode that only records what the agent would have done.
  • DeepSeek labels it a "research prototype for reference only, not an official DeepSeek product", and says it differs from its internal version.

What happened

The essay argues that as single-task coding agents need less hand-holding, the bottleneck shifts to human attention. DeepSeek's proposal is a "Super-agent": one continuous agent that people talk to wherever they already work, such as IM chats and GitHub comments, instead of managing separate sessions. The essay lists four traits: continuous, productive, proactive and persistent. It names five building blocks: a two-level architecture, event-driven triggers, asynchronous multi-channel interaction, separation of compute, state and environment, and an external watchdog. The team writes that it is not proposing new theory but applying classic systems-engineering ideas to agents. It says an internal instance built on DeepSeek Harness already runs continuously, reproducing and fixing issues, responding to code reviews and helping develop Harness itself. The essay also says it is a discussion of architecture ideas, not a description of current DeepSeek Harness features.

The same day, DeepSeek published the prototype on GitHub with numbered design documents (000 Philosophy through 008 Cookbook).

Key details

  • Router/Worker architecture: the main Session uses a dsh-superagent-router preset with a small routing tool set. Each Ticket (unit of work) gets an Executor Session named worker-<ticket id> with the dsh-superagent-worker preset and its own directory. Both presets move shell commands to the background after 5 seconds, so an agent can take new messages at its next step instead of waiting on a long command.
  • Flow: a Source (GitHub, Feishu) produces Triggers. An Eval decides whether to accept, ignore or stop work. Accepting creates a Ticket with an immutable Mandate recording its scope and the policy version it was accepted under. Results go back to the original conversation, for example as a pull request.
  • Authorization: "The host enforces allowed lists, rules and Mandates. Messages, comments and quoted documents are inputs to a decision; they cannot change those permissions." An explicit request must address the agent directly and come from an allowed person. Proactive work needs a rule the team wrote, and the accept mode can be off, observe (the default, record only) or auto.
  • Safety defaults: by default the agent never turns on auto-merge from its own account. People merge pull requests unless the delivery prompt names another account for merging. Executors run commands without approval as the operator's OS user; the philosophy doc advises starting with a short allowed list and record-only proactive work.
  • Philosophy: "Take as little human attention as possible, and give as much value as possible." The agent confirms a request once, stays quiet while it works, and writes again only when it has a result, needs a decision or cannot finish.
  • Open-source vs internal: the README says the published code "is not identical to our internal version or the implementation described in" the essay, and that "some designs discussed in the article are directions for future development and are not implemented in this prototype."
  • Caveat: "Research prototype for reference only, not an official DeepSeek product". DeepSeek says much of it was written by coding agents and calls it research code, not production-ready.
  • Setup: you ask your own coding agent to read SETUP.md and walk you through installation. pnpm check runs typecheck, tests and build. It needs DeepSeek Harness.
  • License: MIT (confirmed via the GitHub API).

Full text

Full text of the original README, reproduced under its MIT License. Relative links point to the source repository. Original: https://github.com/deepseek-ai/dsh-superagent-prototype.

dsh-superagent

Research prototype for reference only, not an official DeepSeek product. This code grew out of our team's day-to-day development work, with much of the engineering done by coding agents. Treat it as research code, not production-ready software. It may still contain bugs, and its coding style and engineering practices may be inconsistent. Review and adapt it before using it in your own environment. We have adapted it for publication, so it is not identical to our internal version or the implementation described in Exploring Super-agent Design: Towards a More Autonomous Agent System. Some designs discussed in the article are directions for future development and are not implemented in this prototype.

dsh-superagent is a proactive coding agent for one GitHub repository, packaged as a bundle for DeepSeek Harness. It listens to GitHub and, optionally, Feishu. When someone allowed asks the agent for work, it opens a work item, works on it in its own agent session and directory, and answers in the original conversation, for example with a pull request. A web panel shows what needs a person.

It is also a way of working with an agent: take as little human attention as possible, and give as much value as possible. An agent that can act for a whole team can also waste a whole team's attention, so it acts only when asked or when a rule the team wrote allows it, and speaks only when someone must act or can use a result. docs/000-philosophy.md explains the principle and what it asks of the operator.

Setup

Setup has many steps, so an agent does it with you. Ask your coding agent:

Read SETUP.md in this repository and set up dsh-superagent with me.

It asks one short question at a time, shows the full plan once, and then installs and configures everything. SETUP.md is what it follows.

What this means for US developers

This is the clearest look so far at how a Chinese frontier lab thinks about long-running team agents. The design questions overlap with what US teams are working on with background agents. The most reusable ideas sit outside any model choice. Authorization lives in the host, not the prompt, so chat messages can't grant themselves new permissions. Each task gets an immutable Mandate. Proactive work starts in record-only mode. And the agent is designed to be quiet by default. You can copy those patterns into your own agent stack whatever model you run. Practical limits: it targets a single repository, its chat integration is Feishu (not Slack), it requires DeepSeek Harness, and DeepSeek itself says it is not production-ready. Workers run commands without approval under your OS user, so sandbox it before you try it. Media coverage frames the release as aimed at Claude Code-style tools (SCMP, Nov 1; The Straits Times, citing Bloomberg). DeepSeek's own materials describe it as an architecture exploration, not a product launch.
